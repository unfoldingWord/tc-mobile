# Device pass for the next tester build

This sheet replaces the checklist on [#974](https://github.com/unfoldingWord/tc-mobile/issues/974),
which still describes the v8 to v9 upgrade and the "New look (O4)" switch, both long gone. It
gathers every device check that the work merged since `tester-build-v1.1.0` (cut 2026-10-14) says
it owes, so a phone owner can run it without reading the PRs.

**Nothing on this sheet has been run.** Every "Result" cell is blank on purpose. Each row's
"Expected" column is what the source PR or issue says should happen, not an observed result.
Where a source says a behaviour is inference, the row says so.

Gathered on 2026-10-26 from the Device checks section of each PR merged after the v1.1.0 tag,
from the open and closed `needs-device` issues, and from the "Not run" sections of the three newest
entries in [the progress tracker](../progress_tracker.md). The sheet describes what is on
`develop`. Cutting the tester build, and the number it gets, is the DRI's call.

## How to run it

- Use one low-end Android phone with the installed app and one iPhone on TestFlight. Rows marked
  "Both" run on each. A row marked "Android" or "iOS" runs on that platform only.
- Run the section 1 rows first, on a phone that already holds recordings made on v1.1.x. Do not
  uninstall to clear a screen: uninstalling deletes the recordings. A phone that has opened a
  newer database schema cannot open an older build again
  ([AGENTS.md](../../AGENTS.md), "A rollback is not free").
- Before you install, write down the shelf: book order, book, chapter and segment names, colours
  and Finished marks. Row 1.3 compares against that note. Start a timer when you open the app in
  row 1.1; row 1.7 records it.
- Row 1.8 can lose recordings. Run it after 1.1 to 1.7, in a browser profile whose recordings you
  can lose. A lost recording there is the result to report.
- Report one comment per phone on the tracking issue: platform, device, OS version, the build
  version shown in the app's footer, and who you are by role. Write a result code (below) against
  each row. A failed row also gets an evidence comment on its source issue or PR.
- The dated run record belongs in `docs/progress_tracker.md`, never in a docblock or a test name.
- Whatever comes back, quote it as seen. Do not round a "could not reach" up to a pass.

Result codes: P = pass, F = fail, N = could not reach, R = recorded. Use R, never P or F, where
the Expected cell gives no expected value, calls a result a report rather than a verdict, or only
asks you to record or note what happened. A cell that does both is mixed: mark P or F on its
outcome, and treat the note as a report to quote. R replaces P or F only when the cell has no
outcome at all. Quote what you saw beside the result.

A cell may instead ban P and list its only outcomes: F, N, and R when the cell defines an R case.
Such a cell overrides the mixed-cell rule above: follow what it says.

When an Action needs a starting state, that setup is part of the Action, even if an earlier row
left the opposite state. Do it before the row, or mark the row N if you cannot.

## 3. Recording, saving and the launch replay (Android and iOS)

Rows 3.2, 3.4 and 3.6 need a build that includes #1725 (merged to `develop` as `6fad1065`). The
footer stamp reads `v<version> · <short sha>`, and the short sha is the commit the build was made
from. Whoever posts the sheet confirms that commit contains #1725 (for example
`git merge-base --is-ancestor 6fad1065 <short sha>` exits 0). On a build without it, the three rows
are N.

On such a build, a launch that saves a take left waiting when the app was killed writes one line to
the problem report: Books ≡ → Send problem report. In the sent text that line reads
`── <UTC time> [pending-take-replayed]`, followed by
`Error: A take left waiting when the app closed was saved (#38)` (the word "Error" is how every
row is written; this one is not a failure). It is the only sign that a take was
waiting. Nothing changes on screen, and the line does not put a mark on ≡. It names no book,
chapter or segment, so plant one waiting take at a time, write down the time of each kill, and
count only lines timestamped after it (the times are UTC). Books ≡ offers the problem report only
when the log holds at least one row.

A missing line is inconclusive, not a pass: the kill may have landed before the app wrote the
waiting copy. Without the line, rows 3.2, 3.4 and 3.6 are N. "The take survived", "the new take
saved" and "nothing came back" are not P on their own. For a P, quote or attach the line in the
evidence comment.
